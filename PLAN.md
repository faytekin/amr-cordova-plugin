# AMR Cordova Plugin - Rewrite Plan

A full, breaking rewrite. The current plugin is a 10-year-old descendant of
`cordova-plugin-admob-free` (verified: the banner layout reflection code,
`CORDOVA_MIN_4`, `OPT_OVERLAP`, and the iOS `resizeContent` comments are copied
verbatim from that lineage). We discard it and rebuild all three layers around
the architecture proven by [`admob-plus`](https://github.com/admob-plus/admob-plus):
a TypeScript Promise API, one class per ad type, a narrow generic bridge, a
single keep-alive event channel, and a **contract-first code-generation** workflow.

> No backward compatibility. There is no dual API and no legacy event names.
> Host apps migrate wholesale. Published as a new repo + new npm package.

This plan incorporates a second-opinion review (Codex/gpt-5.5) plus a study of how
real mediation plugins ship. Key strategic outcomes: a **thin-core +
bring-your-own-adapter** dependency model (mirroring AppLovin MAX's official
Cordova plugin) to kill the native-dependency collisions that forced the old
`zzz` package-name hack, explicit privacy/compliance surface, per-ad state
machines, and `onReset` (WebView reload) handling.

## 1. Locked decisions

| Decision | Choice |
|----------|--------|
| Dependency architecture | **Thin core + bring-your-own adapters** (section 8). Core ships minimal AMR only - NO play-services / network SDKs. Adapters are opted in via `config.xml` plugin variables, materialized by a cordova build hook (exact phase + mechanism decided by a Phase-0 spike; manual `build-extras.gradle`/`Podfile` is the documented fallback). No per-network npm packages. |
| Fullscreen interstitial/rewarded | **v1: in-process `load()` + `show()` only** (the known consumer uses exactly this). AMR's `:adprocess` `AmrAdActivity` path is DEFERRED to a later version (design kept in section 6). |
| Native languages | **Kotlin** (Android) + **Swift** (iOS). Manage the Kotlin-Gradle version axis explicitly (section 8.4) since it is itself a collision vector. |
| www language | **TypeScript**, bundled to one Cordova module + shipped `.d.ts`. |
| Toolchain | **Bun** = package manager + bundler + test runner; `tsc --noEmit` for types. **Consumers never need Bun** (section 2.7). Node only for downstream `cordova build`. |
| Repo layout | **Single package** (no workspaces, no sub-packages). |
| Package name | **`cordova-plugin-admost`** (repo + npm). `cordova-plugin-amr` is an abandoned empty squat on npm - unusable. |
| API parity | Must cover the entire official surface at <https://admost.github.io/amrcordova/> (section 4.7), then extend. |
| Versioning policy | **Thin broker**: pin no network adapter; the consumer owns all adapter versions in their own project config; we cut a release only when the bridge code or AMR's core API changes - never for a network SDK bump (8.1). |

### 1.1 Brand token
The wire/identifier token is **`admost`**: native service name `Admost`, JS global
`window.admost` (or ES import `admost`), event namespace `admost.ad.*`, ad registry
`window.admostAds`, Android package `com.admost.cordova`, iOS class prefix `Amb`.
Anywhere this doc still writes `amr`/`Amr`/`amr.ad.*` from earlier drafts, read it
as this `admost` token.

## 2. How we code this optimally with AI (methodology)

The rewrite is structured so an AI agent produces correct, consistent code with
minimal drift and cheap verification.

### 2.1 Contract-first: one spec generates the bridge in all 3 languages
The largest bug source in a Cordova plugin is the bridge contract (action
strings + event names + payload shapes) drifting between JS, Kotlin, and Swift.
The legacy plugin stores event names as loose string fields in each file. We
eliminate this class of bug. A single `scripts/contract.ts` is the **only** place
actions, events, config keys, payload schemas, and ad classes are declared.
`bun run scripts/gen.ts` emits:

| Generated file | Contents | Consumed by |
|----------------|----------|-------------|
| `src/ts/generated.ts` | `NativeActions`, `Events`, `AdSizeType`, payload types | TS layer |
| `src/android/.../Generated.kt` | `object Actions`, `object Events` consts | Kotlin |
| `src/ios/AmrGenerated.swift` | `AmrActions`, `AmrEvents` structs | Swift |
| `src/browser/AmrProxy.js` | no-op proxy stub | browser platform |

Every generated file carries a `DO NOT EDIT - AUTOGENERATED` header. The AI edits
`contract.ts` and re-runs `gen`, never the outputs. The bridge contract becomes
**provably identical** across languages. Keep `gen.ts` dependency-free TS (no
lodash). Generate only mechanical artifacts (constants, schemas, proxy, plugin.xml
lists) - **never native business logic**.

### 2.2 plugin.xml source lists are generated too
Kotlin/Swift means many small files. `gen.ts` globs `src/android/**/*.kt` and
`src/ios/*.swift` and rewrites the `<source-file>` blocks between
`<!-- AUTOGEN:ANDROID_BEGIN -->`/`END` markers (mirrors admob-plus
`updateConfigXML`). It does NOT touch `SKAdNetworkItems`. Adding a native file
never means hand-editing XML.

### 2.3 Vertical slices, one ad type at a time
Implement+verify a full slice (TS class -> Kotlin -> Swift -> example) for
**Banner first**, then **Interstitial**, then **Rewarded**. Banner exercises the
hardest view-insertion plumbing but is in-process and eyeball-verifiable.
Interstitial adds fullscreen + `:adprocess`. Rewarded reuses interstitial plus
`tag`/reward payload. A regression is always localized to the current slice.

### 2.4 File-per-class, small blast radius
`AdBase` + one file per ad type per platform. No god-files. An AI edit to
`Banner.kt` cannot break `Rewarded.kt`. This is the key departure from the legacy
954-line `Amr.java`.

### 2.5 Explicit per-ad state machine
Every ad is a state machine: `created -> loading -> loaded -> showing ->
dismissed | destroyed` (+ `failed`). All transitions validated in `AdBase`.
This removes the legacy `autoShowInterstitialTemp` / `autoShowVideoTemp` hacks
(which existed precisely because there was no state) and makes concurrent
load/show/destroy deterministic.

### 2.6 Structured error contract
Failures (command rejects AND `amr.ad.loadfail`/`showfail` events) carry a typed
shape: `{ code, message, nativeCode, platform, adId, action }`. No more
`String.format("{ 'error': %d }")` ad-hoc JSON.

### 2.7 Consumers never need Bun
The published tarball contains the **built** `www/amr.js`, the generated native
sources, `types/`, `plugin.xml`, gradle/podspec. A host app builds with only
Node + Cordova. Bun/tsc/codegen are dev-time only and excluded from the npm
`files` set. (Common npm-publish failure mode - section 9.)

### 2.8 Guardrails & gates
- **Golden contract test** (`bun test`): generated enums match a committed snapshot.
- **JS unit tests**: mock `cordova.exec`; assert each class calls the right action
  with the right payload, `on()` filters by `adId`, `show()` auto-loads, state
  transitions hold.
- **`tsc --noEmit`** required gate; `.d.ts` is the app developer's contract.
- **Native lint**: `ktlint`/`detekt`, `swiftlint`.
- **Build-only integration CI** + **conflict matrix** (section 9): build the
  example app with collision-prone plugins (Firebase/push) installed.
- **Behavior**: real ad load/show verified manually (ad SDKs too flaky for E2E).

### 2.9 Conventions (English-only per repo rules)
English everywhere; UI thread for all SDK/UI calls; iOS selector name == action
string; Conventional Commits; one slice per PR/commit group.

## 4. The generated contract

### 4.1 Actions (JS -> native)
`ready`, `start`, `configure`, `setConsent`, `isPrivacyConsentRequired`,
`requestTrackingAuthorization` (iOS ATT), `startTestSuite`, `adCreate`, `adLoad`,
`adShow`, `adHide`, `adIsLoaded`, `adDestroy`, `trackIap` (Android IAP revenue
tracking, official `trackIAPForAndroid`). Deferred from v1: `adLoadAndShow` (the
`:adprocess` path - no known consumer uses it; section 6).
Note: `isPrivacyConsentRequired` is delivered as a document EVENT carrying
`data.status` (`'GDPR'` etc.), not a boolean-resolving action - match the real
usage in `irregular-verbs`.

Correction: `trackIap` is NOT dropped. The official docs document
`trackIAPForAndroid({purchaseData, signature, currency, priceAmountMicros})`; it was
merely broken/unwired in this particular fork (the `trackPurchaseForAndroid` stub).
The rewrite implements it properly.

### 4.2 Events (native -> JS), namespaced, carry `adId`
`amr.ready`, `amr.ad.load`, `amr.ad.loadfail`, `amr.ad.show`, `amr.ad.showfail`,
`amr.ad.click`, `amr.ad.impression`, `amr.ad.dismiss`, `amr.ad.statuschange`,
`amr.ad.complete`, `amr.ad.reward`, `amr.ad.revenue` (ILRD/paid - see 4.5),
`amr.banner.size`.

| New event | Replaces legacy |
|-----------|-----------------|
| `amr.ad.load` | `onBannerReady`, `onInterstitialReady`, `onVideoReady` |
| `amr.ad.loadfail` | `onBannerFail`, `onInterstitialFail`, `onVideoFail` |
| `amr.ad.show` | `onBannerShow`, `onInterstitialShow`, `onVideoShow` |
| `amr.ad.dismiss` | `onBannerHide`, `onInterstitialDismiss`, `onVideoDismiss` |
| `amr.ad.statuschange` | `onInterstitialStatusChanged`, `onVideoStatusChanged` |
| `amr.ad.complete` | `onVideoComplete` |
| `amr.ad.reward`, `amr.ad.revenue`, `amr.ad.click`, `amr.ad.impression`, `amr.banner.size` | (new) |

### 4.3 Config keys (platform-suffixed kept)
`applicationIdAndroid`/`applicationIdIos`, `bannerId*`, `interstitialId*`,
`videoId*`, `subjectToGdpr`, `userConsent`, `subjectToCcpa`, `canRequestAds`.
Per-ad: `adUnitId` (zone id), `size`/`adSize`, `position`, `offset`,
`bannerWidth` (iOS), `tag` (rewarded). TS API exposes clean
`boolean | undefined`; mapped to AMR's tri-state `"-1"|"0"|"1"` at the native edge.

### 4.4 Ad classes & id
`BannerAd` | `InterstitialAd` | `RewardedAd` extend `MobileAd`. **`id` defaults to
an auto-generated unique value** (not `adUnitId`) so two ads can share a zone;
`adUnitId` stays a separate field. Registered in `window.amrAds`.

### 4.5 Revenue / impression-level data
AMR's `onReady(network, ecpm)` already carries network + eCPM that the legacy code
throws away. Surface it: `amr.ad.revenue` / `amr.ad.impression` payloads include
`{ network, ecpm, currency?, precision? }`. Modern ad apps need this from day one.

### 4.6 Contract version
`start` resolves `{ version, contractVersion }`; the TS layer can warn on a native
/JS contract mismatch.

### 4.7 Official API parity (must cover everything in the docs)
The official guide (v1.3.0, March 2025) is the floor; the rewrite must support all
of it, then extend with the modern additions above.

| Official feature | Official call | New API |
|------------------|---------------|---------|
| Init | `startWithConfig({applicationIdAndroid, applicationIdIos, userConsent, subjectToGdpr})` | `Admost.start(config)` |
| GDPR | `userConsent`/`subjectToGdpr` as `"0"`/`"1"` | `setConsent` (TS bool -> tri-state at edge) |
| Banner | `loadBanner`/`hideBanner`/`destroyBanner` + events `onBannerReady/Load/Fail/Show/Destroy` | `BannerAd` load/hide/destroy |
| Interstitial | `loadInterstitial({..., autoShowInterstitial})`/`showInterstitial`/`destroyInterstitial` + `onInterstitial Ready/Fail/Show/Dismiss` | `InterstitialAd` |
| Rewarded | `loadRewardedVideo({..., autoShowVideo})`/`showRewardedVideo`/`destroyRewardedVideo` + `onVideo Ready/Complete/Fail/Show/Dismiss` | `RewardedAd` |
| Test Suite | `startTestSuite()` | `Admost.startTestSuite()` |
| IAP tracking | `trackIAPForAndroid({purchaseData, signature, currency, priceAmountMicros})` | `Admost.trackIap(...)` (Android) |
| DFP/AdMob mediation | custom-event classes `admost.sdk.dfp.AmrDfpCustomEventBanner` / `AmrDfpCustomEventInt` | keep the dependency that provides them + document dashboard config (no new bridge code) |
| `autoShow*` flags | `autoShowInterstitial`/`autoShowVideo`/`autoShowBanner` | supported as options for parity; idiomatic path is explicit `load()` then `show()` |
| AppLovin key | `applovin.sdk.key` manifest meta-data | contributed by the AppLovin adapter package (8.2) |

Notes: the official page is acknowledged as outdated; treat its surface as the
minimum, not the ceiling. `onBannerLoad` vs `onBannerReady` both map to
`admost.ad.load`; `onBannerDestroy` maps to `admost.ad.dismiss`/destroy.

### Real-world usage (validation target: `irregular-verbs`)
The plugin's real consumer is `/Users/aytekin/Documents/repos/irregular-verbs`
(`www/js/ads.js`). Concrete findings that shape v1:
- **Only in-process load + manual show is used.** `loadInterstitial({autoShowInterstitial:false})`
  -> `onInterstitialReady` -> `showInterstitial()`; same for rewarded;
  `loadBanner`/`hideBanner`. `loadAndShow*` (`:adprocess`) is NEVER called -> defer it.
- **`autoShow*: false`** is the real pattern (load, wait for the ready event, then
  show on demand). Keep explicit `load()`/`show()` idiomatic; `autoShow` optional.
- **Consent/ATT are external plugins**: Google UMP (`window.Ump`) for consent,
  `cordova.plugins.idfa` for ATT. `startWithConfig` only gets app IDs +
  `canRequestAds` (string). Our consent surface can be thin.
- **`isPrivacyConsentRequired` is a document EVENT** carrying `data.status`
  (`'GDPR'` etc.), not a boolean-resolving action. Match that shape.
- **Rewarded reward logic depends on event ordering**: `onVideoComplete` (reward
  earned) fires before `onVideoDismiss` (acted on at close). Preserve this order in
  the new `admost.ad.complete` -> `admost.ad.dismiss` sequence.
- **Test bed**: real Admost app IDs + zone IDs, builds for android/ios/browser -
  use it for the Phase-0 spike and behaviour validation.
- Migration: `ads.js` must be rewritten to the new Promise/namespaced-event API
  (accepted breaking change); it is the concrete validation of the rewrite.

## 6. The `:adprocess` fullscreen flow (Android) - DEFERRED from v1
> STATUS: deferred from v1. The known consumer (`irregular-verbs`) uses in-process
> `load()` + `show()` and never calls `loadAndShow*`, so v1 ships in-process only.
> The design below is retained for a later version - this removes the rewrite's
> single riskiest piece from v1 scope.

- Manifest (kept): `multiprocess="true"`, `screenOrientation="landscape"`,
  fullscreen theme. **Rename the process** from generic `:adprocess` to
  `:amradprocess` to reduce cross-plugin collision.
- Launch: `Intent(activity, AmrAdActivity::class)` with extras `ZONE_ID`,
  `IS_REWARDED`, `APP_ID`, `CONSENT`, `CAN_REQUEST_ADS`, `SUBJECT_TO_GDPR`;
  `cordova.startActivityForResult(this, ...)` after
  `cordova.setActivityResultCallback(this)`.
- **Fix vs legacy**: use `cordova.startActivityForResult` for BOTH interstitial
  and rewarded (legacy used `activity.startActivityForResult` for interstitial,
  bypassing Cordova's result routing - a latent bug).
- **Process-death handling (best-effort, NOT guaranteed)**: persist the pending
  request across `onSaveInstanceState` and try to recover the activity-result
  callback on resume. Do not promise guaranteed recovery; design an explicit
  fail/cancel contract (emit `dismiss`/`showfail`) for the lost-callback case.
  Cordova docs warn the result callback can be lost across process death.
- Cross-process state: AMR init/consent is NOT shared across the process; that is
  why config is passed via Intent extras. Keep that, and keep it in sync with the
  in-process consent values.
- The commented-out `FLAG_ACTIVITY_NEW_TASK` lines are intentional; do not add.
- iOS has no `:adprocess`; `adLoadAndShow` there is load-then-show.

## 7. Privacy & compliance (new; legacy predates these)

- **iOS `PrivacyInfo.xcprivacy`**: ship a privacy manifest declaring data use +
  required-reason APIs; bundle via `plugin.xml`. Mandatory for App Store.
- **iOS ATT**: `requestTrackingAuthorization` action wrapping
  `ATTrackingManager`; keep `NSUserTrackingUsageDescription` (already in plugin.xml).
- **Android `AD_ID` permission**: declare
  `com.google.android.gms.permission.AD_ID` (required since target API 33 for
  advertising id); allow host apps to remove it if they opt out.
- **SKAdNetworkItems**: ship the full Admost list as a convenience superset (extra
  IDs are harmless and it is NOT tied to which adapters the consumer picks, so it
  needs no release per adapter bump). Consumers may trim it. `gen.ts` leaves it
  untouched.
- Consent/ATT are handled by EXTERNAL plugins in the real app (Google UMP
  `window.Ump` + `cordova.plugins.idfa`). AMR's own surface stays thin:
  `canRequestAds` passthrough + the `isPrivacyConsentRequired` event (status
  string). GDPR/CCPA flags remain available for apps that do consent through AMR.

## 8. Dependency architecture (thin core + bring-your-own adapters)

The fix for the collisions that forced the old `zzz` hack. Checked against the
two closest real precedents - **neither ships per-network npm packages**, so the
earlier "adapter packages" idea is dropped:
- **AppLovin MAX** (a mediation SDK like AMR), official Cordova plugin
  (`AppLovin/AppLovin-MAX-Cordova`): ships ONLY the base SDK
  (`com.applovin:applovin-sdk` / `AppLovinSDK` pod). Mediation adapters are NOT in
  the plugin; the developer pastes a gradle/Podfile snippet (from AppLovin's web
  picker) into their OWN build. No variables, no scripts, no sub-packages.
- **firebasex**: single package + a post-install script that rewrites plugin.xml
  from `config.xml` variables, "since Cordova does not support using plugin
  variables to optionally include plugin dependencies."

### 8.1 Model: thin broker (follow AppLovin-MAX)
Core = minimal AMR runtime only; networks are bring-your-own. The plugin is a
**broker**: it references and pins NO network adapter. The consumer declares the
adapters and versions they want in their own project; the plugin just wraps AMR's
API. Consequences (this is the whole point):
- We do NOT bump adapter versions in this repo and do NOT cut a release when a
  network SDK updates. Routine adapter version maintenance leaves this repo
  entirely (the old `update-amr` skill stops being the recurring workflow).
- The consumer picks whatever adapter version they want and aligns it with their
  own other plugins (Firebase / maps / push) - the real collision cure.
- The ONLY native dependency the plugin pins is the AMR CORE SDK it compiles
  against (8.2), and even that version is overridable via a plugin variable.
- A plugin release is needed only when our bridge code changes or AMR's core API
  changes - rare.

### 8.2 Core package (`cordova-plugin-admost`)
Ships only what the plugin itself needs: `com.admost.sdk:amr` +
`com.admost.sdk:cordova-plugin` (provides `AmrAdActivity`) +
`com.admost.sdk:admost-adapter` + the lightweight identifier libs AMR requires
(appset / ads-identifier). iOS: `AMRSDK`. **The core does NOT pull
`play-services-ads` or any network SDK**, so the plugin alone can never trigger
the play-services/Firebase collision. (Pin the exact minimal set in Phase 2 by
reading AMR's POMs - verify whether AMR core hard-requires anything heavier.)

### 8.3 Networks are bring-your-own (including Admob)
The developer enables each network in their OWN build, exactly like AppLovin. We
ship the friction-removers: a `build-extras.gradle` template (this persists across
`cordova platform add`, unlike editing `platforms/android/app/build.gradle`) and a
`Podfile` block, plus a per-network "enable X" doc.
- Android: `implementation 'com.admost.sdk:admob-adapter:...'` / `applovin-adapter`
  / `unity-adapter` / ... + that network's Maven repo (ironsource `is.com`,
  mintegral, pangle) in `build-extras.gradle`.
- iOS: `pod 'AMRAdapterAdmob'` / `AMRAdapterApplovin` / ... in the `Podfile`;
  network-specific keys (AppLovin `applovin.sdk.key`, Admob app id, etc.) per the doc.
Because the developer owns these lines, version alignment with their other plugins
is in their hands - the real cure for the collisions.

Version hygiene for everything we ship or recommend in snippets:
- No `+`/open versions; pin tested defaults.
- No default `resolutionStrategy.force`; prefer Gradle constraints / alignment;
  `force` only as a documented host escape hatch.
- Narrow excludes only; never blanket-exclude play-services/Firebase/AndroidX.
- Maven deps only; never bundle `.jar/.aar`.

Where the consumer declares this (DECIDED location: `config.xml`). The plugin
ships a build hook + a network registry; the consumer sets only version variables.
**Mechanism detail is open and a Phase-0 spike decides it.** The naive
"`before_build` edits the generated `Podfile`/gradle" is WRONG: `cordova build`
runs `before_build` -> `prepare` -> `compile`, and `prepare` regenerates those
files, overwriting the edit. Robust options to spike:
- modify the plugin's OWN declared deps so Cordova's normal `prepare` generates the
  right `Podfile`/gradle (e.g. an npm post-install rewrite of `plugin.xml`, the
  firebasex way - clean generation but a documented first-install reinstall gotcha), or
- a hook at the correct phase (`before_prepare`, or `after_prepare`/`before_compile`
  that injects then re-runs `pod install`).
Parse variables straight from `config.xml` (do not rely on `package.json` sync).
If iOS automation proves fragile, **fall back for v1** to the manual
`build-extras.gradle` + `Podfile` snippet (AppLovin's model): declaration is not in
config.xml then, but it is robust.

The hook ships a **network registry** so the consumer never types Maven URLs or
coordinates - only versions. For each known network the registry holds (stable,
non-version-churning) data:
- Android: the `com.admost.sdk:<network>-adapter` coordinate + the vendor Maven
  repo to add (ironsource `is.com`, mintegral, pangle, ...).
- iOS: the `AMRAdapter<Network>` pod.
The consumer sets only the version variable(s) for the networks they want; unset
= not included. Escape hatch: an unknown/exotic network can still be added by the
consumer in their own `build-extras.gradle`/`Podfile`. We pin NO version - the
registry holds only coordinates/URLs, which do not change per SDK release, so a
network SDK bump still needs no release from us.

### 8.3.1 Per-platform versions (critical)
AMR's versions diverge completely between platforms - they are different version
schemes, not just different numbers:

| Package | Android (`com.admost.sdk:*`) | iOS (pods) |
|---------|------------------------------|------------|
| Core SDK | `amr:3.2.8` | `AMRSDK ~> 1.5` |
| Admob | `admob-adapter:24.0.0.5.a49` | `AMRAdapterAdmob ~> 13.1` |
| AppLovin | `applovin-adapter:13.6.2.a49` | `AMRAdapterApplovin ~> 13.6` |
| Unity | `unity-adapter:4.17.0.a49` | `AMRAdapterUnity ~> 4.17.1` |
| Facebook | `facebook-adapter:6.21.0.a49` | `AMRAdapterFacebook ~> 6.21` |

So there is NO single version per package. The fix matches this plugin's existing
convention (`applicationIdAndroid`/`applicationIdIos`): **platform-suffixed
declarations**, routed to the right native build.

- Option 1 (build-extras.gradle + Podfile) handles this for free: the Android
  version lives in `build-extras.gradle`, the iOS version in the `Podfile` -
  separate files by nature, and the shape matches what Admost's own docs hand you.
- Option 2 (config.xml) needs `*_ANDROID` / `*_IOS` suffixed variables, and the
  `before_build` hook routes `_ANDROID` -> gradle and `_IOS` -> Podfile.

Example consumer `config.xml` (option 2):
```xml
<plugin name="cordova-plugin-admost" spec="^3.0.0">
  <variable name="ADMOST_SDK_VERSION_ANDROID" value="3.2.8" />
  <variable name="ADMOST_SDK_VERSION_IOS" value="1.5" />
  <variable name="ADMOB_ADAPTER_VERSION_ANDROID" value="24.0.0.5.a49" />
  <variable name="ADMOB_ADAPTER_VERSION_IOS" value="13.1" />
  <!-- networks left unset are simply not included -->
</plugin>
```

Decided: **config.xml + hook**, per the tenet that the consumer declares
everything in `config.xml`. Per-platform is handled by suffixed variables
(mirroring this plugin's `applicationIdAndroid`/`applicationIdIos` convention);
the hook routes `_ANDROID` -> gradle and `_IOS` -> Podfile. Naming is systematic:
`ADMOST_ADAPTER_<NETWORK>_<ANDROID|IOS>_VERSION` (+ `ADMOST_SDK_VERSION_ANDROID`/
`_IOS` for core). The consumer always writes a bare version (e.g. `13.1`); the hook
owns the platform syntax (Android coordinate, iOS `~> 13.1`) deterministically. The
core SDK default ships in the plugin's gradle (Android) + podspec (iOS).

### 8.4 Kotlin version axis (the tradeoff we accepted)
Kotlin adds a `kotlin-gradle-plugin` version to the host build - itself a
collision vector. Mitigate: rely on cordova-android's built-in Kotlin support
(`GradlePluginKotlinEnabled`), pin `GradlePluginKotlinVersion` to a current LTS,
expose it as a plugin variable, and keep `kotlin-stdlib` aligned. Document the
required preference. (admob-plus runs Kotlin in production without issue.)

### 8.5 iOS packaging
- `use_frameworks!` is global and affects other pods. Note: AppLovin's official
  plugin sets `use-frameworks="true"` in its podspec, so a mediation SDK may
  require it. Verify whether AMRSDK/adapters need it; if so, treat it as a
  deliberate, documented choice. Our own Swift compiles as plugin source (`@objc`).
- Pod versions: narrow ranges that leave the resolver room (neither wide `>=`
  nor hard exact pins).
- **Watch**: CocoaPods trunk is reportedly going read-only (~Dec 2026) and
  cordova-ios supports SPM - design SPM-readiness in, but VERIFY this timeline
  before relying on it (unconfirmed at time of writing).

### 8.6 Thin-broker guardrails (compatibility is now the consumer's)
By not pinning adapters we hand AMR-core/adapter compatibility to the consumer.
So we help them:
- Ship a documented **tested compatibility matrix** (which AMR core + adapter
  versions we verified) in the README; refresh it as we test new combos.
- `start()` reports the native AMR core version (and loaded-adapter info where the
  SDK exposes it) so apps/CI can assert.
- Fail-fast or warn on known-incompatible combinations the hook/runtime can detect.
- Release-policy nuance: a network *version* bump needs no release, but if a
  registry entry's **coordinate / Maven repo / pod name** changes (not the
  version), that DOES need a plugin release; an AMR core *major* needs a bridge release.
